Feature C — SIGINT / Comms Intelligence Feed

Question 1 of ~4: Where does the SIGINT data come from?

The current simulation has no comms intercept data. The comms_intelligence Kafka topic is referenced in the project spec but the sim engine doesn't generate any SIGINT events yet. Before we design the UI, we need to decide where the data comes from.

A

Extend the simulation engine

Add SigintIntercept events to the sim. Assets with radios periodically emit comms; enemy EW assets (the EW Radar Vehicle already in the scenario) detect and intercept them. Intercepts flow through the existing WebSocket diff payload as a new sigint_intercepts field — same pattern as detections and mission_updates.

Pros

  • Intercepts are tied to real asset positions
  • EW asset has a meaningful role
  • No new infrastructure

Cons

  • More backend work (sim engine changes)
B

Standalone synthetic generator

A lightweight background task in the API generates plausible intercept events on a timer, independent of the sim tick loop. They flow through the existing WebSocket but aren't correlated with asset positions or EW logic.

Pros

  • Fast to implement
  • No sim engine changes

Cons

  • Fake data, no sim correlation
  • EW asset remains decorative
C

Kafka-native (as originally specced)

The API consumes the comms_intelligence Kafka topic and forwards messages over the WebSocket. Matches the project's Layer 1 / Layer 2 architecture in CLAUDE.md. Keeps the data pipeline architecturally honest.

Pros

  • True to original architecture
  • Real pipeline integrity

Cons

  • Requires Kafka running + wired
  • Most infrastructure work
